    Canonical affordance examples

    One worked example of every affordance the SKILL.md mentions. Each section below uses the exact markup pattern you should reuse — copy the structure, swap the content, leave the classes and attribute names alone.

    Annotatable section

    Every section that the user might annotate uses this exact shape. The id drives the in-page anchor and ToC entry; the data-annot-id drives the export payload. Use the same value for both unless you have a reason not to.

    <section class="annot" id="auth-middleware-flow" data-annot-id="auth-middleware-flow">
  <h2>Auth middleware flow</h2>
  <p>Body of the section.</p>
</section>

    The widget appends the notes box automatically — don't add one yourself. The ToC entry is built from the first <h2> or <h3> inside the section.

    Callouts

    Three variants. Use the plain .callout for neutral asides, .callout-warning for pitfalls or "watch out for" content, .callout-question for open questions or autonomous-run assumptions (see below).

    Note

    Plain callout. Useful for "by the way" content that isn't a warning or a question.

    Watch out

    Warning callout. Use sparingly — if everything is a warning, nothing is.

    Open question

    Question callout. The annotation widget can't attach to a callout directly; if you want this question to be annotatable, wrap the whole section it lives in with data-annot-id.

    Autonomous-run assumption (Non-interactive mode)

    When no human is available to answer a question, replace the question with this exact pattern. Drop it at the top of the relevant section so reviewers can annotate it directly.

    Autonomous-run assumption

    No user was present to answer "which areas should I research?". I assumed the relevant code is the four SKILL.md files under skills/ plus .claude-plugin/plugin.json. If a reviewer disagrees, annotate this section to redirect.

    Code references and code blocks

    Inline file references use .code-ref — the JS makes them click-to-copy. For multi-line code, use a regular <pre><code> block.

    Example: see skills/plan-repl/SKILL.md:42 for the original transition convention, or templates/base.html for the page shell.

    // multi-line code goes in pre+code, no .code-ref class
function example() {
  return "use code-ref for inline file paths, this for code blocks";
}

    Risk table

    Three-column table for tight tabular risk data. The likelihood column gets a .pill with one of three severity classes. Don't expand the table to four or more columns — at that point a vertical list of cards is easier to scan.

    RiskLikelihoodMitigation
    Migration runs against a dirty working tree. High Refuse to start when git status shows changes.
    Annotation IDs drift between regenerations. Med Use descriptive slugs; audit before each regen.
    localStorage growth on long-lived tasks. Low Clear after each annotation round.

    Phased timeline

    Ordered list of phase cards. The CSS numbers them automatically; use <h3> for the phase title so the heading lines up with the badge. Nested lists inside a phase don't get numbered — the > li selector keeps the counter at the top level.

    Todo list with checkboxes

    For todo.html only. Each checkbox needs data-todo-id so its state persists to localStorage and rides along in the annotation export under checks.

    Inline SVG diagram

    Hand-author SVG when the change involves multiple components interacting, or you need a data-flow / sequence picture markdown can't render. Reuse the design tokens with a small inline <style> inside the SVG so colors stay consistent.
